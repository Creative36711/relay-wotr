# ScriptCat transport decisions

This journal contains only transport decisions using the `D-###` format. Since D-003 the transport holds no mirrored foreign journal: foreign decisions may appear only as citations, and foreign prefixed numbers are never presented as our own.

## D-001 (1.16.8) — Isolate transport CI and keep the decision gate meaningful

**Date:** 2026-11-22 · **Status:** accepted.

The relay-wotr pull-request gate is a single aggregate required check on GitHub-hosted runners, with read-only repository permissions, no secrets, pinned actions, full history and an explicit role-zone preflight. Operational WOTR decisions remain in the upstream mirror; `docs/DECISIONS.md` is reserved for transport decisions so preflight's existing `^##\s+D-\d+` matcher can enforce one new decision and its contract key without exceptions.

**Rollback:** remove the CI workflow and this decision/contract entry together; do not weaken or broaden the preflight decision matcher to accommodate mirrored WOTR decision IDs.

## D-002 (1.16.9) — Authority через контракт профиля: три варианта, default «оставить как есть»

**Date:** 2026-11-22 · **Status:** accepted (шаг 0: ADR + контракт; выбор варианта (а)/(б) — отдельным решением Мастера, per-project).

### Контекст

Транспорт сейчас несёт проектные процессные docs как собственное содержимое: зеркало из десяти путей проекта (`docs/REGULATION.md`, `docs/regulation-digest.md`, `docs/PHASES.md`, `docs/DECISIONS-UPSTREAM.md`, `docs/missions/TEMPLATE.md`, `docs/missions/WOTR-1.1.md`, `docs/missions/WOTR-1.2.md`, `docs/agents/cost-gates.md`, `docs/agents/troubleshooting.md`, `docs/agents/roles/localization-cultural-qa-engineer.md`), краткий регламент, вшиваемый сборкой в бандл, и профиль `tools/script-cat/wotr-project.json` с идентификаторами проекта. Правка проектных docs меняет транспорт; один репозиторий привязан к одному проекту.

Карточка TRANS · NEU требует нейтральности: один транспорт — несколько проектов, зависимость односторонняя (проект подстраивается под контракт, транспорт о проектах не знает). **Шаг 0 — только настоящий ADR и контракт**: переноса содержимого и удаления зеркал нет; старый путь остаётся рабочим, зелёным и обратимым, пока новый путь не принят.

### Варианты

**(а) artifact-by-reference.** Реестр проекта публикует краткий регламент контент-адресованным артефактом в Drive (чтение — через существующий drive-gateway, новых capability не запрашиваем). Профиль хранит `{fileId, sha256, regulationVersion}`; транспорт перед каждым dispatch читает артефакт и сверяет хэш. В git транспорта не попадает ни байта проектных docs. Плюсы: минимальный контракт, верификация до отправки, ноль проектных байтов. Минусы: публикация артефакта — работа проекта, fail-closed чтение — работа транспорта; доверие к fileId приходит из профиля.

**(б) transport-as-library.** Транспорт публикует версионированный выпуск (src-фрагменты, schema, guard, тесты); бандл собирает проект собственным CI, deploy — per-project. Транспорт проектные docs не читает вовсе. Плюсы: полная независимость, версии под контролем проекта. Минусы: интеграционная стоимость на каждый проект, публикация и синхронизация релизов транспорта.

**(в) embedded-mirror — текущее поведение.** Десять зеркальных путей и вшитый digest остаются как сейчас; нейтральность достигается только схемой контракта, а не содержимым. Плюсы: ноль работы, статус-кво зелёный, переход per-project обратим. Минусы: проектные docs остаются байтами транспорта; правка проекта меняет транспорт.

**Default: (в) оставить как есть.** Новый путь (а)/(б) включается per-project и обратим; до его принятия зеркало и digest остаются рабочими (инварианты ниже).

### Контракт (нормативная часть; любое изменение — только новым D-### вместе с release)

1. **Контракт версии транспорта.** semver в `@version` (`tools/script-cat/src/00-header.js`) плюс changelog в `docs/scriptcat-update.md`; preflight требует подъёма версии только вместе с правкой `src/**`. Breaking-изменение любого пункта контракта ниже — отдельный release транспорта с подъёмом @version и новой записью D-###; правки контракта в зеркале проекта или в чужом репозитории запрещены.
2. **Схема профиля проекта (минимальный set).**
   - `projectId`, `repo` — идентичность проекта и целевой репозиторий;
   - `notion` — data sources проекта (roles, missions, requests, questions);
   - `authority: { kind, fileId | url, sha256, regulationVersion }` — источник регламента: `kind: "embedded-mirror"` (сейчас; fileId/sha256/regulationVersion не применяются) или `kind: "artifact"` (вариант (а));
   - `dispatch: { markerPrefix, roleZones, costGateMatrix }` — общий префикс имён result-маркеров, зоны записи по ролям, ссылка на матрицу Cost gate проекта.
   Проектные значения никогда не хардкодятся в код транспорта — они читаются из профиля во время выполнения. Поля профиля вне этого набора — приватная деталь транспорта и меняются без breaking-контракта.
3. **Формат result-marker.** Имена `CF_*_RESULT` с JSON-телом по матрице `markers` в `contracts/agent-protocol.json` (эталон) и `docs/agents/markers.md`; разбор — лестница `parseMarker` в `src/13-arena-messages.js`. Префикс имён задаёт профиль (`dispatch.markerPrefix`, сейчас `CF_`).
4. **Формат evidence-строки.** Отчёт строчный: строка evidence = команда, rc, существенный вывод, длительность в секундах (шаг «команды/rc/существенный вывод» — `docs/agents/cost-gates.md` §7); шапка отчёта фиксирует tested SHA, Node version, итоги (pass/fail) и каждый `not run`. Ровно этот формат обязателен для отчётов транспорта в `docs/evidence/`.

Всё, что вне этих четырёх пунктов, — приватная деталь транспорта.

## D-003 (1.17.0) — Транспорт без проектного содержимого: digest и профиль — вход сборки (шаг 2/2, вариант (б))

**Date:** 2026-11-22 · **Status:** accepted (шаг 1 — OPS · RELAY-BUILD-1, Accepted; настоящий шаг закрывает цепочку NEU).

### Контекст

D-002 зафиксировал контракт профиля и оставил старый путь (embedded-mirror) рабочим. Теперь принят вариант **(б) «транспорт как библиотека и контракт»**: транспорт не хранит и не читает проектное содержимое, операция синхрона зеркала исчезает вместе с зеркалом.

### Решение

1. **Удаление одиннадцати путей** одним коммитом с проверками, которые на них падают: `docs/REGULATION.md`, `docs/regulation-digest.md`, `docs/PHASES.md`, `docs/DECISIONS-UPSTREAM.md`, `docs/agents/cost-gates.md`, `docs/agents/troubleshooting.md`, `docs/agents/roles/localization-cultural-qa-engineer.md`, `docs/missions/TEMPLATE.md`, `docs/missions/WOTR-1.1.md`, `docs/missions/WOTR-1.2.md`, `tools/script-cat/wotr-project.json`. Команда `git ls-tree -r --name-only HEAD -- <все 11 путей>` даёт пустой вывод — команда и вывод фиксируются в evidence-отчёте.
2. **Регламент — вход сборки.** Placeholder `@@REGULATION_DIGEST@@` остаётся в `src/01-config.js`; вход сборки — `--digest <путь>`; без параметров сборка даёт нейтральный бандл с пустым блоком регламента и rc 0. Каждая сборка записывает `contracts/build-manifest.json` `{schema, version, digest: null | {version, sha256}}`; `--check` сверяет bundle, coverage и manifest.
3. **Оракул сохраняется, проверка переезжает на вход.** `regulation-oracle.mjs` не удаляется: шапка переданного digest'а («Версия N.N») сверяется с build-manifest (`assertDigestAgainstManifest`); при `digest: null` функция возвращает `null` — неприменимость показывается явно в прогоне и в отчёте, никогда молча и никогда не как skip.
4. **Guard только расширяется.** К прежним паттернам добавляются нейтральные паттерны проекта (имя, репозиторий, префиксы карточек, Notion/Drive идентификаторы, процессные пути); существующие проверки не выключаются; `UPSTREAM.md` — единственное исключение для новых паттернов; всё, что на новые паттерны падает, удаляется тем же коммитом.
5. **Изоляция проектов закреплена пробой:** два sanitized-фиктивных проекта живут в одном рантайме изолированно (prompt, зоны, лимиты, очереди), удаление одного не ломает другой; собранный бандл не содержит проектных строк; отсутствие одиннадцати путей — отдельной проверкой.
6. **Release.** @version поднят в `src/` и инструментах (1.16.9 → 1.17.0), changelog — в `docs/scriptcat-update.md`, `protocolVersion` контракта 1.11 → 1.12, настоящая запись — своим номером; чужие номера не используются.

### Инварианты

- Ноль проектных байтов и ноль сетевых чтений проектных репозиториев: вход только параметрами сборки.
- Удаление содержимого ≠ удаление оракула: проверка версии существует на входе и показывает неприменимость явно.
- Guard расширяется только добавлением паттернов; not run ≠ pass; таймаут ≠ skip.
- Односторонняя зависимость: `UPSTREAM.md` — единственное исключение.
- Свои номера `D-###`; чужие — только цитатой и без чужих префиксов в этом журнале.
- Breaking оформлен своим release; правок в чужих репозиториях нет.
- Без секретов, retail-ссылок и чужих идентификаторов; новых capability не запрашивается.

### Rollback

Откат — одним коммитом: вернуть одиннадцать путей, прежний CLI сборки, прежний оракул и прежние guard-паттерны; @version и запись D-003 откатываются вместе с ними. Пер-проектная обратимость D-002 сохраняется.

### Fail closed (нормативно)

При `authority.kind: "artifact"` перед каждым dispatch: прочитать артефакт, посчитать sha256, сверить с профилем. Несовпадение хэша **или** отсутствие артефакта — отказ dispatch с явной ошибкой, в которой названы ожидаемый и полученный хэш и `regulationVersion`; warning и «продолжить молча» запрещены. При `authority.kind: "embedded-mirror"` (текущий режим) поведение не меняется.

### Portability guard: нейтральность (нормативно)

`tools/script-cat/portability-guard.mjs` обязан падать, если в любом файле транспорта, кроме `UPSTREAM.md`, встретится имя проекта, его repo, ID Notion/Drive, префикс карточки или проектный путь. Расширение — только добавлением паттернов: существующие проверки не выключаются и не ослабляются. Активация нейтральных паттернов идёт вместе с новым путём (переносом содержимого и профиля наружу), чтобы режим embedded-mirror оставался зелёным до принятия нового пути; сегодняшний охват guard'а (бывшие идентификаторы, provenance, provision) сохраняется без изменений.

### Изоляция мультипроектности (нормативно)

Разные authority-артефакты живут в одном рантайме без взаимного влияния: prompt, зоны, лимиты и очереди каждого проекта изолированы профилем; удаление одного проекта не ломает остальных. При выборе (а) или (б) добавляется тест: собранный бандл режима artifact не содержит проектных строк (имя, repo, ID, префиксы, пути); вшитый digest остаётся только в режиме embedded-mirror.

### Приложение: план и стоимость удаления embedded-mirror (если выбраны (а) или (б); само удаление — отдельной карточкой на стороне проекта)

**Пути, которые перестают копироваться в транспорт** (сейчас это зеркало из десяти): `docs/REGULATION.md`, `docs/regulation-digest.md`, `docs/PHASES.md`, `docs/DECISIONS-UPSTREAM.md`, `docs/missions/TEMPLATE.md`, `docs/missions/WOTR-1.1.md`, `docs/missions/WOTR-1.2.md`, `docs/agents/cost-gates.md`, `docs/agents/troubleshooting.md`, `docs/agents/roles/localization-cultural-qa-engineer.md`.

**Что придётся перестроить:** `tools/script-cat/build.mjs` (сборка не стартует без `docs/regulation-digest.md` и сверяет версию digest'а с REGULATION через `regulation-oracle.mjs`), `relay-regulation-digest-smoke` (фиксирует проектные строки в digest'е), зоны в `prompts-smoke` и guard-extra-список (REGULATION, digest, scriptcat-update сейчас вне нейтральных паттернов), `wotr-project.json` наружу (профиль приходит во время выполнения), ссылки acceptance-report на `docs/evidence/<version>.md`.

**Стоимость (оценка):** 10 путей, две точки сборки (digest-зависимость build.mjs и assertDigestVersionMatches), не меньше трёх тестов на пересмотр, вынос профиля, один ход удаления с полным `verify:scriptcat`; протокол маркеров не меняется. Удаление — только после принтия (а)/(б) и зелёного нового пути; при ветке (в) ничего из этого не делается.

### Инварианты

1. Ноль проектных байтов в репозитории транспорта как цель: проектные docs транспорт получает только как данные профиля во время выполнения (или не получает вовсе при (б)); на шаге 0 ничего не переносится и не удаляется.
2. Зависимость односторонняя: проект подстраивается под контракт транспорта; транспорт не знает о существовании WOTR, OpenBFME и других проектов; ни одна правка проектных docs не создаёт задачи в очереди транспорта.
3. Транспорт не выделяет номера `WOTR-*` и не копирует чужие журналы: собственный журнал — только `D-###`; ссылки на чужие решения допускаются только цитатой, не как номер, занятый у нас.
4. Ни одна проверка не выключается и не ослабляется: режим embedded-mirror остаётся зелёным, пока новый путь не принят; переход включается per-project и обратим конфигом; not run не превращается в pass, таймаут не становится skip.
5. Секреты, токены, retail-ссылки и персональные пути в git нет; новых capability не запрашивается — артефакты читаются существующим drive-gateway.
6. Breaking-изменение контракта — только собственный release транспорта с подъёмом @version и записью D-###; правки контракта в зеркале проекта или в чужом репозитории не делаются.

### Не делаем (шаг 0)

Перенос содержимого, удаление зеркал, правки guard'а, dispatch и тестов. Исполнение нормативных пунктов «fail closed», «нейтральность guard'а» и «изоляция» — отдельными ходами после выбора варианта; на этом шаге зеркало, digest и профиль не меняются.

**Rollback:** удалить секцию D-002 и ключ `d002` из `contracts/agent-protocol.json` вместе; контракт выше перестаёт действовать, поведение транспорта не менялось.

## D-004 (1.18.0) — Квоты Arena по аккаунтам: лимит принадлежит аккаунту, работа остаётся последовательной

**Date:** 2026-11-23 · **Status:** accepted (решения владельца: «Доступность» отдельным полем, связка почт локально в ⚙, лимит административного аккаунта — жёсткая пауза, «работать нечем» — один вопрос Координатору). **Клаузула о последовательности отменена D-009 (1.19.0); остальное действует.**

### Контекст

Пять ролей одной миссии идут строго последовательно, но квота суточного лимита Arena — у аккаунта, а аккаунтов четыре (Firefox Multi-Account Containers). Пока аккаунт был один, исчерпанная квота означала остановку всего процесса: пауза `daily-limit`, класс `master`, и ожидание полуночи. Владелец поставил задачу разложить квоты: лимит одного аккаунта не должен останавливать работу остальных, а административные роли (Coordinator, Warden, Transport Maintainer) не должны делить квоту с исполнителями.

Второе требование — не сломать последовательность: смысл раскладки в том, чтобы ход шёл дальше, а не в том, чтобы запускать несколько шагов сразу.

### Решение

1. **Данные.** В базе «Роли» — два аддитивных поля: «Аккаунт» (`select`, метки `account-1`…`account-4`; это заглушки, владелец заменит имена) и «Доступность» (`select`: «ОК» / «Лимит»). «Аккаунт» — непрозрачная метка, адреса в ней нет. В «Доступность» пишет только транспорт; **«Статус» остаётся полем Мастера** и лимитом не переписывается — иначе возврат «Активна» затёр бы решение Мастера, принятое за эти часы, а в «Статус» пишет ещё и provisioning.
2. **Адреса входа** хранятся только локально: ⚙ «Подключения» → «Аккаунты Arena», строки «метка = почта» (ключ `cfn-account-map`). В Notion они не попадают: база общая на команду, почта — это вход.
3. **Признак лимита один и достоверный:** видимый индикатор «Daily usage limit reached» в поле ввода на странице роли. Он атрибутируется аккаунту этой роли. Текст ошибки, тишина агента и tool-call limit лимитом аккаунта не считаются: один сбой не должен отправлять в карантин целый аккаунт.
4. **Отметка лимита.** Локальная запись `cfn-account-limits` со сроком «ближайшая полночь по Москве» (UTC+3 круглый год, без переходов на летнее время) плюс durable-признак «Доступность» = «Лимит» у ролей аккаунта — чтобы другой браузер и человек видели, почему роль не выдаётся.
5. **Поведение при лимите рабочего аккаунта.** Задание роли не ставится в очередь (`sendToRole`) и не вставляется в заблокированное поле (`consumePending`); карточка остаётся в Ready с прежним `Sequence`. Единица работы — **вкладка в своём контейнере**: `location.assign` контейнер не меняет, поэтому «уйти этой вкладкой на другой аккаунт» нельзя — откроется та же учётная запись. Уходят не вкладки, а ход: остальные вкладки-контейнеры крутят свои шаги и забирают общую очередь (`K.pending`, `K.expect`) сами. Вкладка лимитированного аккаунта при этом **не ставит паузу и молчит до сброса окна**: `pause` общая на все вкладки, и «лимит рабочего аккаунта» остановил бы именно работу остальных. `accountsTick` возвращает вид остановки (`admin` / `worker` / `unbound`), чтобы вызывающая сторона отличала «стоим» от «здесь нечего делать».
6. **Лимит административного аккаунта** останавливает цикл паузой `account-limit-admin` (класс `master`, пункт `money`, входит в `HEAL_HOLDING`): спрашивать Координатора нечем, он сам на этом аккаунте. Текст паузы называет роли и время сброса.
7. **Возврат ролей — попытка, а не допущение.** Таймера в полночь нет: вкладку к тому времени закроют. На каждом шаге проверяется, прошёл ли срок; на странице аккаунта — погас ли индикатор. Погас → «Доступность» возвращается **только** тем строкам, которые отметил транспорт и где всё ещё стоит «Лимит»; индикатор ещё виден → отметка остаётся и выдача не возобновляется. Старые незакрытые карточки подхватываются обычной очередью: `Ready` не переставляется, `Running` с живым ожиданием не снимается.
8. **Незакрытый ход не теряется.** Если лимит наступил, пока ожидание стояло, уборка фантомов и таймауты брошенных карточек его не трогают (`accountHoldsExpect`): ответ агента читается только на его странице, и возврат `Running` в `Ready` отправил бы его в пустоту (D-045). После сброса ход восстанавливается тем же ожиданием, без перевыдачи.
9. **Аккаунт вкладки проверяется, но не переключается.** Читается подпись сайдбара (почта): наблюдённый селектор, запасной по признакам класса, затем клик `Expand sidebar` и повторное чтение; режим иконок — «неизвестно». Непрочитанная подпись — предупреждение в журнале, а не остановка: свёрнутый сайдбар не повод стоять. Разворот сайдбара — один раз на страницу: повторять его каждые пятнадцать секунд значило бы драться с Мастером, который свернул панель намеренно.
   **Расхождение не чинится из скрипта и не останавливает другие вкладки.** Контейнер открывает человек, а `pause` — общая. Поэтому вкладка, стоящая в контейнере чужого аккаунта, просто пропускает шаг, сказав об этом в журнале один раз (в ручном режиме — сразу: Мастер нажал «Шаг» и должен увидеть причину). То же правило у перехода: `navigateTo` не ведёт на роль другого аккаунта — её страница открылась бы в этом контейнере, то есть чужим аккаунтом. Пауза `account-wrong` из списка видов пауз убрана совсем: она ставилась только отсюда, а отсюда её больше не ставят — иначе остановка одной вкладки гасила бы остальные три.
10. **Координатор видит причину.** В план идут `accountPlanNote` (недоступные аккаунты со сроком), дефект роли называет лимит, а когда вся оставшаяся работа лежит на лимитированных аккаунтах — один вопрос на окно лимита (`accountIdleNote`): взять другую карточку или вернуть `blocked`, то есть пауза миссии. «Один раз» отсчитывается от **фактической отправки плана** (`accountIdleAskedMark` после `sent`), а не от сборки текста: неотправленный план (капча, пауза, ожидание) не должен съедать вопрос.
11. **Раскладка не правится скриптом, но называется вслух.** Проверка подключений («Проверить и сохранить») добавляет к отчёту то, что видит в «Ролях»: административные роли разложены по нескольким аккаунтам, на административном аккаунте есть рабочие роли, у активных ролей не заполнено поле «Аккаунт». Это предупреждения, а не отказ: старая база работает без них.
12. **Паритет «Шаг» и автоцикл.** Всё новое живёт в `tick()` и `navigateTo()`, поэтому оба пути получают одно поведение; отдельной ветки в кнопке нет. `protocolVersion` остаётся 1.12: маркеры, их поля и бюджеты не менялись.

### Откат

Убрать чтение полей «Аккаунт»/«Доступность» и вызовы `accountsTick`/`accountVerdict` из `tick` и `navigateTo`, вернуть в `28-cycle.js` прямой вызов `monitorDailyLimit()`; поля в Notion остаются как история и не мешают. Без правки `src/**` это одна новая сборка с прежним поведением — очередь, ожидания и карточки не переставляются ни на одном шаге.

## D-009 (1.19.0) — Асинхронный транспорт: состояние в Google Sheets, служба вместо вкладки, диспетчер вместо предела «одна карточка»

**Date:** 2026-11-26 · **Status:** accepted (решения владельца: состояние — Google Sheets; вкладки становятся «глупыми» — готов; клаузула D-004 о последовательности — отменяется; контейнеров сейчас четыре, число будет расти; интерфейс ScriptCat убирается сразу, не поэтапно).

### Контекст

D-004 разложил квоты по аккаунтам, но оставил работу последовательной: «смысл раскладки в том, чтобы ход шёл дальше, а не в том, чтобы запускать несколько шагов сразу». На живых прогонах это стало главным ограничением. Владелец, дословно: «очень сложно и неудобно»; «скрипт должен проверять, какой контейнер закончил работу и тут же передавать ход обратно координатору, даже если другие контейнеры ещё работают».

Причина была не в квотах, а в носителе состояния. Очередь и ожидание жили в `GM_setValue` одной вкладки: две вкладки не видели друг друга (D-006 пришлось лечить «будильником»), а всё, что знал транспорт, умирало вместе с окном. Единицей работы была вкладка, поэтому одновременная работа была невозможна в принципе, а не по настройке.

### Решение

1. **Состояние переезжает в Google Sheets.** Книга «Relay · WOTR — состояние транспорта» (`1_MohMfnUvl40CT689gfch_MgPtzqokSw5Bylbl89PFQ`), шесть листов: «Состояние», «Слоты», «Очередь», «Выдачи», «События», «Настройки». Порядок колонок задаётся **только** `relay/src/schema.mjs`; запись с лишним полем — ошибка, а не тихая потеря данных.
2. **Слот — это контейнер плюс аккаунт.** Новая база Notion «Слоты» (`4246f0cf-5705-810d-997a-f8cf79aba45f`, data source `4246f0cf-5705-81b8-8914-000b74d974e7`) под той же страницей, что «Роли». Заполнено четыре строки: `admin` / arena-creative / creative36711@gmail.com (административный), `worker-1` / arena-yandex / Creative36711@yandex.ru, `worker-2` / arena-list / creative36711@list.ru, `worker-3` / arena-textile / textile33b@gmail.com. Новый контейнер — новая строка; код не меняется ни в одном месте.
3. **Роли перестают быть «местом».** «Роли» остаются справочником «кто есть кто»; привязки роли к контейнеру больше нет. В каждом рабочем слоте доступны все рабочие роли, в административном — только Coordinator, Warden и Transport Maintainer. Правило D-004 «административная роль не уходит на рабочий слот» сохранено и проверяется по колонке «Функция» строки очереди, то есть работает даже без доступа к Notion.
4. **Единица работы — строка очереди, а не вкладка.** Одновременно может идти несколько выдач (лист «Выдачи»), у каждой свой `Run ID`. Освобождение одной выдачи возвращает ход сразу (`releaseAndRequeue`), не дожидаясь остальных: это и есть асинхронность, ради которой всё переделано.
5. **Количество одновременных выдач решает Координатор.** Предел `cycle.maxParallel` (по умолчанию 2) — только ограничение сверху. Координатор может попросить меньше (`requested`), и диспетчер не «добирает» до предела: «если в моменте выгоднее сделать одну карточку, чем одновременно четыре, он должен выбирать первый вариант… смотреть, что требует проект». Действует и на `pull` вкладки, чтобы предел нельзя было обойти прямым запросом.
6. **Служба вместо вкладки.** Новый слой `relay/` (Node, без сборки): `schema`, `store`, `slots`, `queue`, `dispatch`, `accounts`, `events`, `incident`, `settings`, `setup`, `protocol`, `service`, `server`, `demo-store`. Протокол вкладки — шесть действий (`hello`, `pull`, `beat`, `report`, `event`, `bye`); решений она не принимает.
   **Состояние дел на 1.19.0: клиента протокола в вкладке ещё нет.** `tools/script-cat/src/**` по-прежнему читает очередь из `GM_setValue` (`K.pending`/`K.expect`); служба проверена своими тестами и пультом, но живой цикл она пока не ведёт. Пока клиент не написан, единственный рабочий путь — прежний; служба работает параллельно и ничего не ломает, потому что её никто не спрашивает. Это записано явно, чтобы «переделали» не означало «уже работает иначе».
7. **Интерфейс ScriptCat убирается сразу.** Пульт — статическая страница службы (`relay/web`): шаг, пауза, режим, очередь, слоты, журнал с фильтром по виду, пакет инцидента. Никакой сборки: страница обязана открываться, даже когда транспорт сломан. **На 1.19.0 панель ScriptCat ещё на месте** — она уходит тем же коммитом, что и клиент протокола (п. 6), иначе останется цикл без единого рабочего интерфейса.
8. **Журнал общий, с дорожкой человека.** Лист «События» пишут все вкладки и пульт, у записи есть слот, аккаунт, вкладка, вид и уровень. Действия человека (`ui`) отделены от действий транспорта намеренно: «нажали паузу» и «notion не ответил» — разные факты, и в одном тексте они читаются неверно.
9. **Пакет инцидента вместо простыни в промпте.** Maintainer получает окно событий ±10 минут из всех слотов, отдельную дорожку UI, сторожевые и сетевые срабатывания, **таблицу всех живых выдач** и проверку «чей это run id» (найден / чужой карточке / уже закрыт / не найден / похож на другой). Число событий ограничено, при переполнении сохраняются ошибки и строки самого инцидента, а не просто последние.
10. **Настройка — минимум ввода.** Мастер ищет базы «Роли», «Слоты», «Запросы» и папку логов сам (`planSetup`), пишет только найденное и не затирает существующее пустотой. Agent URL перестаёт быть ручным полем. Инвариант, закреплённый тестом `auditSettings`: **в расширенных настройках нет ни одного ключа, без чего цикл не работает**; у всех расширенных есть значение по умолчанию, а обязательные (`project.name`, `notion.rolesDb`, `notion.slotsDb`) лежат в базовых.
11. **Гонка за строку разрешается статусом, а не удачей.** Захват (`leased`, «Взял слот», «Взято в») пишется в таблицу до журнальной записи о выдаче. Прямой CAS у коннектора Sheets нет, поэтому «проверить свежее состояние → записать» и повторная проверка на шаге; для двух одновременных шагов по одной книге в будущем остаётся место для `LockService` в шлюзе Drive.
12. **Повторный `pull` узнаёт свою выдачу.** Вкладка, потерявшая ответ (перезагрузка, таймаут), получает ту же выдачу, а не «слот занят». Повторный отчёт по закрытой выдаче — не поломка и не новая работа: `duplicate`, а не ошибка разбора.
13. **Ответ принимается строго.** Выдача есть, она жива, агент не сказал «не смог», маркер указывает именно на неё. Всё остальное — разбор с пакетом. `Accepted` по-прежнему выставляет Coordinator, а не транспорт.

### Что отменяется из D-004

Клаузула «работа остаётся последовательной» и мотивировавшая её фраза «смысл раскладки в том, чтобы ход шёл дальше, а не в том, чтобы запускать несколько шагов сразу» **отменяются**. Очередь `K.pending`/`K.expect` больше не общая в прежнем смысле: её заменяют листы «Очередь» и «Выдачи». Всё остальное в D-004 остаётся в силе: лимит принадлежит аккаунту, «Доступность» пишет только транспорт, «Статус» — поле Мастера, административный аккаунт не делит квоту с исполнителями, срок лимита — ближайшая полночь по Москве.

### Откат

Служба `relay/` удаляется целиком, вкладка возвращается к прежнему режиму: `28-cycle.js` снова читает `K.pending`/`K.expect` из `GM_setValue`. Данные в книге и в базе «Слоты» остаются как история и не мешают: старый код их не читает. Откат не переставляет карточки и не снимает ожиданий — он просто перестаёт спрашивать службу.

## D-008 (1.18.4) — Возврат хода: подпись сайдбара не единственный свидетель

**Date:** 2026-11-24 · **Status:** accepted (продолжение D-007; решение владельца — «тот же класс ошибки»).

### Контекст

Журнал после 1.18.3:

```
22:24:44 Аккаунт вкладки: аккаунт вкладки не прочитан (icon-collapsed): сверка с «creative36711@list.ru» пропущена.
22:25:03 Ответ UX & Modding Auditor записан, PR не нужен, задача → Submitted.
22:25:03 Сейчас /agent/01a20e78-… — открываю страницу «Coordinator»: туда возвращается ход.
```

Вкладка стояла на странице UX & Modding Auditor (контейнер `list.ru`) и открыла адрес Координатора в этом же контейнере — чужим аккаунтом. Ровно тот же отказ, что D-007 вылечил для отправки задания, но в другой двери: возврат хода.

Причина точная: `navigateTo` проверял только подпись сайдбара (`accountMismatchSync`). Подпись была свёрнута до иконок — `icon-collapsed`, — проверка честно ответила «сравнивать нечего», и переход состоялся. То есть защита зависела от того, развёрнута ли панель.

Вторая проблема в той же ветке: `goTo` снимал очередь (`K.pending = null`) **до** перехода. С запретом перехода это означало бы потерянный ход.

### Решение

1. **`navigateTo` спрашивает страницу, а не только подпись.** Второй свидетель — `accountPageCheck` (D-007): доказанно чужой аккаунт — перехода нет, ход отдаётся своей вкладке (`wakeOnce`). Подпись сайдбара остаётся первым, дешёвым свидетелем; страница проверяется, когда подписи нет или она молчит.
2. **Своя страница проверку пропускает.** Если `roleFromPath()` — это и есть роль назначения, переходить можно: адрес роли в своём контейнере и есть нужная вкладка.
3. **Очередь снимается только после разрешённого перехода.** `goTo` сначала спрашивает, чья страница; на чужой — очередь, карточка и журнал остаются, а в журнале сказано, чья вкладка нужна. Иначе запрет перехода превращал бы защиту в потерю хода.
4. **Непрочитанная подпись по-прежнему не запрет.** `unknown` не останавливает работу; запрещает только доказанное расхождение адресов.

### Откат

Убрать ветку `accountPageCheck` из `navigateTo` и проверку из `goTo` (вернуть снятие очереди в начало); `@version` и запись D-008 откатываются вместе. Логика D-007 для `sendToRole` не затрагивается.

## D-007 (1.18.3) — Задание забирает своя вкладка; чужая за ним не ходит

**Date:** 2026-11-24 · **Status:** accepted (решение владельца: только разворот логики, вкладки открывает человек).

### Контекст

Журнал первого живого прогона после D-006:

```
21:19:20 Выдан ход UX & Modding Auditor: «WOTR-1.1 · A2 · UX & modding audit»
21:19:20 Задание «UX & Modding Auditor»: бужу остальные вкладки — отправит та, чей это аккаунт.
21:19:20 Перехожу к «UX & Modding Auditor», чтобы отправить задание.
21:19:48 Не нашёл поле ввода на странице адресата (contenteditable 0, textarea 1 …):
         задание осталось в очереди и не потеряется.
```

Вкладка Координатора сделала обе вещи сразу: разбудила нужную вкладку (D-006 сработал) и тут же сама пошла по адресу роли — в своём контейнере. Страница открылась чужим аккаунтом, поля ввода нет, задание осталось в очереди, а Мастер увидел «работает не очень хорошо».

Причина: у `sendToRole` был **свой** переход (`location.assign(role.url)`), отдельный от `navigateTo`. Проверку контейнера в D-004 получил только `navigateTo`, а этот путь писался раньше и остался без неё. D-006 добавил «просьбу», но не убрал «толкание».

### Решение

1. **Толкать можно только в свой контейнер.** Перед переходом `sendToRole` спрашивает, чья это страница (`accountPageCheck`). Доказанно чужой аккаунт — перехода нет, очередь не трогается: её заберёт вкладка, чей это аккаунт. Разбудили её в D-006.
2. **Страница, которая сама называет себя этой ролью, проверку проходит.** Если `roleFromPath()` возвращает id этой роли, третья сторона тут ни при чём: сверка нужна ровно тогда, когда адрес роли открыт в чужом контейнере.
3. **Кеш подписи привязан к пути.** `readAccountEmail` кеширует прочитанный аккаунт, и на новом пути подпись прошлой страницы выглядела бы подписью новой. Поэтому соответствие «путь → аккаунт» запоминается (`accountPageMap`), а аккаунт роли берётся из Notion (D-005).
4. **Непрочитанная подпись работу не останавливает.** `unknown` — не запрет: свёрнутый сайдбар или поздняя отрисовка не повод стоять. Запрещает только доказанное расхождение — как в D-004.
5. **Второй рубеж — там, где вставляется текст.** Если страница всё же оказалась чужой, `ensureComposer` узнаёт об этом один раз, а не ждёт поле двадцать секунд, закрывая плашки. `consumePending` говорит «не отправляю: страница открыта аккаунтом X, роль закреплена за Y» и завершает шаг без пятисекундного повтора.
6. **Тик тоже это понимает.** Когда подпись сайдбара не прочитана, тик проверяет страницу тем же `accountPageCheck` и уходит в `idleWrongAccount` — а тот будит нужную вкладку (D-006), вместо попыток найти поле ввода, которого не будет.
7. **Закрытую вкладку по-прежнему открывает человек.** Автоматическое открытие вкладки в чужом контейнере — задача расширения, не userscript; владелец выбрал ручной вариант. В журнале сказано, чья вкладка нужна.

### Откат

Убрать вызов `accountPageCheck` из `sendToRole`, `ensureComposer`, `consumePending` и из проверки тика, ветки `foreign` вместе с `pendingRoleRow` и `accountPageMap`; `@version` и запись D-007 откатываются вместе. Очередь и ожидание не менялись, данных в Notion решение не пишет — откат безопасен для хода.

## D-006 (1.18.2) — Будильник вкладок: одна кнопка вместо угадывания контейнера

**Date:** 2026-11-24 · **Status:** accepted (решение владельца: вариант «разбудить все вкладки», кнопка рядом с «Шаг»).

### Контекст

D-004/D-005 разложили квоты по аккаунтам, но работа осталась распределённой по вкладкам-контейнерам. Владелец на первом живом прогоне: Координатор поставил карточку `UX & Modding Auditor` (аккаунт `list.ru`), а вкладка админского контейнера, увидев чужой адресат, молча ушла — очередь осталась ждать нажатия в другой вкладке. Формулировка владельца: «переключаться между вкладками и угадывать, где нажать Шаг — слишком сложно; хочу нажать в любой вкладке и чтобы работа пошла».

`location.assign` контейнер не меняет, `pause` общий: ни «перейти», ни «остановить остальных» из одной вкладки нельзя. Остаётся общее хранилище.

### Решение

1. **Отметка «работа есть», а не переход.** Кнопка **📣 Все вкладки** на панели (рядом с «Шаг» и «Включить») пишет общий ключ `cfn-wake-all` с окном жизни: 10 минут на нажатие, не больше 30 минут подряд. Она ничего не отправляет, не выдаёт задание и не уводит страницу — только снимает у вкладок «спящий» режим.
2. **Откликается та вкладка, чья это работа.** Разбуженная вкладка выполняет шаг по обычному пути, только если для её роли действительно есть работа: неотправленная очередь её `roleId` или ожидание ответа её роли (`wakeWorkHere`). Чужие задания её не будят — иначе три вкладки начали бы искать работу на пустом месте. Непрофильная страница разбуженной вкладки идёт к работе, как «Шаг».
3. **Источник отметки — не только кнопка.** Вкладка, поставившая задание роли другого аккаунта (`sendToRole` → `wakeForPending`), будит остальных сама: после решения Координатора ход не должен ждать Мастера. Своё задание отметку не ставит — эта вкладка и так не спит.
4. **Повторяющиеся причины отмечаются не чаще раза в 10 минут.** «Не на своём аккаунте», «аккаунт в лимите», «роль живёт в другой вкладке» проверяются каждый тик; без ограничения они продлевали бы окно каждые 15 секунд, и ручной режим незаметно стал бы автоциклом (`wakeOnce`).
5. **Оба «отдыха» будят остальных.** Вкладка, ушедшая из-за чужого контейнера (`idleWrongAccount`) или из-за лимита своего аккаунта (`idleLimitedAccount`), ставит отметку: работа могла быть поставлена до того, как выяснилась причина.
6. **Две вкладки одного аккаунта не делают шаг дважды.** Разбудить можно и две вкладки одного контейнера; шаг берёт одна — короткая заявка `cfn-wake-doing:<аккаунт>` (`wakeClaim`, 90 секунд). Ключ на аккаунт, а не общий: две вкладки разных контейнеров с разными заданиями — не дубль, а нормальный ход. Заявку берёт только вкладка, у которой работа уже своя (`pending`/`expect`), а не та, что лишь пойдёт на чужую страницу. Живой шаг продлевает заявку (`wakeHold` из `stepAlive`, не чаще раза в 30 секунд), поэтому долгое ожидание мержа не выглядит брошенным. Протухшая заявка не блокирует: закрытая посреди шага вкладка не держит остальных дольше полутора минут.
7. **Ручной режим не расширен.** Будильник — единственное исключение из «фон без нажатия ничего не делает»: он делает ровно то, что сделало бы нажатие «Шаг» в этой вкладке. Автоцикл и «Шаг» идут тем же путём (`tick`), отдельной ветки нет.
8. **Чего будильник не может.** Открыть неоткрытую вкладку в чужом контейнере — только человек. Если нужная вкладка закрыта, отметка истечёт; в журнале сказано, что работа ждёт своего контейнера.

### Откат

Убрать чтение `cfn-wake-all` из `tick` (вернуть `if (!auto && !fromToggle) return;`), вызовы `wakeForPending` в `sendToRole`, `wakeOnce` в двух «отдыхах» и в отказе `navigateTo`, проверку `wakeClaim` и кнопку из панели; `45-wake.js` не подключать. Ключи `cfn-wake-*` в хранилище останутся и не помешают — их никто не читает.

## D-005 (1.18.1) — Почта аккаунта живёт в Notion: ввод адресов в транспорт убран

D-004 (п.1–2) закрепил: в «Ролях» — непрозрачная метка, адрес входа — только локально в ⚙ «Подключения» → «Аккаунты Arena» (ключ `cfn-account-map`, строки «метка = почта»), потому что база общая на команду, а почта — это вход. Владелец сменил требование: почта **должна** указываться в Notion и работать оттуда — поле «Аккаунт» он уже заполнил адресами, и дублирование их в транспорте лишний шаг. Почта может меняться и у каждого аккаунта своя — это не должно быть проблемой.

1. **Notion — единственный источник почты.** Поле «Аккаунт» базы «Роли» (select) хранит адрес аккаунта; значение им же служит меткой аккаунта, ключом лимитов и ожидаемым адресом сверки вкладки. Пустое поле — «аккаунт не размечен», как и раньше.
2. **Локальной связки нет.** Секция⚙ «Аккаунты Arena» осталась справочной (называет источник адресов), поле ввода и разбор «метка = почта» удалены; ключ `cfn-account-map` не читается и не пишется, прежние значения в storage не мешают и не используются.
3. **Сверка — против Notion.** Подпись сайдбара сравнивается прямо с полем «Аккаунт» роли (`accountMail(label)`). Значение, не похожее на адрес, — предупреждение в журнале и пропуск сверки (как раньше без связки), не остановка; непрочитанный сайдбар — тоже предупреждение. Блокирует только доказанное расхождение — D-004 п.10 без изменений.
4. **Смена почты — без действий в браузере.** Новое значение подхватывается при следующем чтении «Ролей» (кеш ≤10 минут). Смена посреди окна лимита не теряет отметку: снятие ищет строки по `pageId` без привязки к прежнему адресу, повторная отметка забирает `touched` из старого ключа, тик снимает прошедшее окно и по `roleId` роли.
5. **Квоты D-004 не меняются.** Лимит/квота — состояние аккаунта, «Доступность» пишет только транспорт, «Статус» — поле Мастера, `accountsTick` admin/worker/unbound, удержание незакрытого хода, план и вопрос Координатора — как в D-004; меняется только источник адреса. `protocolVersion` остаётся 1.12: маркеры, их поля и бюджеты не трогались.

### Откат

Вернуть поле ввода и `parseAccountMap` в `07-connections-ui.js`, `accountMap`/`accountMailFor` в `44-accounts.js` и ключ `cfn-account-map` в `02-profiles-core.js`, восстановить чтение связки в `accountVerdict`/`accountMismatchSync`; @version и запись D-005 откатываются вместе. Данные Notion остаются: старый код прочитает адреса как метки, сверка почты превратится в предупреждение «адрес не задан» и не остановит работу — откат безопасен для цикла.

## D-010 (1.19.1) — Зона роли объявлена один раз, а PR сравнивается с точкой ветвления

**Дата:** 2026-11-23 · **Статус:** принято.

**Причина.** Обязательный гейт «Transport Maintainer zone preflight» покраснел на PR, где в коде не было ни одной ошибки: зона роли была записана строкой в `.github/workflows/scriptcat.yml`, и в этой копии недоставало `relay/**`. Локально `--zone` обычно не передавали, поэтому устаревшая копия жила только в CI и срабатывала ровно на том PR, который стоило разрешить.

Вторая ложная тревога того же рода — `git diff origin/main` в CI. GitHub проверяет коммит слияния, `main` успевает уйти вперёд, и в диффе всплывают файлы, которых ветка не касалась. Зона честно сообщала «вне зоны: relay/**», хотя это были чужие коммиты, слитые в обратную сторону.

**Решение.**

1. Зона роли объявлена константой в `tools/script-cat/preflight.mjs`. `--zone` остаётся для ручных прогонов и проб; пустой аргумент означает «зона роли». Копий списка больше нет: workflow вызывает `node tools/script-cat/preflight.mjs` без аргументов.
2. В CI (`GITHUB_BASE_REF`) файлы считаются от `merge-base HEAD origin/<base>` — от точки ветвления. Что принёс `main` после неё, не наша зона и не наш блокер.
3. Проверка «ветка не отстала» в CI не выполняется: PR по определению может стоять на старой базе, и `behind` там растёт от чужих коммитов. В рабочей копии перед push правило прежнее.

**Инварианты.** Гейт по-прежнему блокирует чужой файл в PR, маркеры конфликта, несобранный бандл, версию без правки `src/**` и два решения в одном PR. `relay/**` входит в зону роли, как и в `ALLOWED_PATHS` сборки; расхождение этих двух списков и было причиной.

**Откат.** Вернуть строку `--zone "…"` в workflow и ветку `git diff origin/main` в `changedFiles`; пробы «без --zone…» и «в PR зона считается от merge-base…» откатываются вместе с решением.

## D-011 (1.20.0) — Экземпляры (роль × контейнер), жёсткие пределы и расход квот по аккаунтам

**Дата:** 2026-11-23 · **Статус:** принято.

**Причина.** Три требования владельца, которые старые решения не покрывали.

1. «У каждой роли может быть несколько Agent URL, так как в каждом контейнере будут одинаковые роли, кроме админского». D-009 п. 3 оставил роль без привязки к контейнеру, но хранил адрес в строке роли — одном `url`. Notion не выражает «несколько адресов на роль» ни `url`, ни `rich_text` со списком.
2. «Если координатор сделал три карточки для Integration Auditor, наверное будет неправильно, если он разошлёт сразу все три карточки разным агентам Integration Auditor из разных контейнеров». Транспорт этого не запрещал: `planBatch` не смотрел на роль.
3. «Квота на аккаунт, а не на агента… на каждом аккаунте будут дублироваться все роли». Из этого следует, что роль доступна в нескольких слотах и выбирать надо аккаунт, а не порядок в таблице.

**Решение.**

1. **Экземпляр — пара (роль, слот).** Новый лист «Экземпляры»: `Роль, Слот, Agent URL, Состояние, Создан, Job ID, Последняя жизнь, Заметка`. Ключ — нормализованная пара (регистр и внутренние пробелы не различаются). Строка «Ролей» остаётся про постановку: зона, гейт, репозиторий, функция.
2. **Ленивое создание вместо ручного.** Если пары нет, служба ставит в очередь строку `Вид = provision` для этого слота; вкладка слота забирает её отдельным входом и создаёт агента. Задание не выдаётся чужому слоту и не раздаётся обычной выдачей.
3. **Наследование адреса.** Пока у пары нет своего экземпляра, действует `Agent URL` из строки роли. Старые базы работают без миграции; ручной перенос адресов при обновлении не требуется.
4. **Пределы — в коде, а не в промпте.** `cycle.maxPerRole` (по умолчанию 1) запрещает вторую выдачу роли, пока идёт первая; вторая выдача той же карточки запрещена при любом лимите. Отказ происходит до захвата строки и называет занятый слот и карточку. Промпт Координатора объясняет правило, но не является его носителем: промпт — просьба, транспорт — запрет.
5. **Расход квот ровный.** Слот выбирается по наименьшему числу живых выдач аккаунта, а не по порядку в таблице; аккаунт с отметкой лимита берётся последним. Иначе первый аккаунт выгорает за день, а остальные простаивают.
6. **`Статус` и `Agent URL` перестают быть блокером.** Блокером остаётся фаза миссии (`Ждёт`): роли, которые ещё не должны работать, агента не получают. Отсутствие адреса — сигнал создать агента, а не повод отказать.

**Инварианты.** Административная роль по-прежнему не уходит на рабочий слот; административный слот не берёт рабочие роли. `maxPerRole` не отменяет запрет двойной выдачи карточки. Экземпляр без адреса не считается готовым. Лист «Экземпляры» создаётся службой при первом обращении, если у токена есть право правки.

**Откат.** Вернуть выбор слота по порядку (`byType[0]`), убрать проверку `roleLimits` из `planOne`, перестать читать «Экземпляры» (наследование адреса из строки роли сохраняет работу на старых базах само по себе). Данные в книге остаются: лишний лист не мешает.

## D-012 (1.21.0) — Цикл ленивого создания замкнут: вкладка возвращает адрес

**Дата:** 2026-11-23 · **Статус:** принято.

**Причина.** Самопроверка D-011 нашла, что ленивое создание выдаёт задание, но не принимает результат. Замыкания не было ни с одной стороны.

1. **Адресу некуда деться.** `agentReady` не существовал вовсе: вкладка создавала агента, а записать пару (роль, слот) в «Экземпляры» было некому. Пара навсегда оставалась «нет агента», и каждая следующая карточка этой роли снова требовала создания. Внешне цикл «работает» — задание выдаётся, агент появляется, — и именно поэтому ошибка не видна без проверки: она не останавливает работу, она делает её бесконечной.
2. **`pull` возвращал «жди» тому, кто сам должен создать.** Первый `pull` нового контейнера всегда был пустым: вкладка вставала в ожидание собственной работы. Владелец просил, чтобы отсутствие агента не было блокером, — а оно было блокером на первом же запросе.
3. **Адрес всегда пустой.** В выдаче стояло `plan.role?.url`, но план строился с `roles: []`, и роль по имени не находилась никогда. Ошибка тихая: выдача приходила, агент получал задание без адреса и ждал.

**Решение.**

1. **Действие протокола `agent`.** Вкладка сообщает роль, слот, адрес и признак неудачи. Служба пишет пару в «Экземпляры» (`agentReady`), закрывает задание `provision` и пишет событие. Адрес берётся из экземпляра пары, а не из строки роли.
2. **Задание отдаётся той же вкладке.** `pull` при отсутствии агента ставит задание и сразу возвращает его этому слоту. «Жди» остаётся только случаю, когда задание уже взяла другая вкладка того же слота.
3. **Открытое задание — это `waiting` и `leased`.** Вторая вкладка читала `leased` как «не ждущее», заводила второе задание и создавала второго агента на ту же пару. Защита в памяти (`PROVISION_CLAIM_MS`) закрывает гонку в пределах процесса, но не между процессами — проверка открытости закрывает и её.
4. **Причина отказа доезжает до вкладки.** «Агента ещё нет» и «прошлая попытка не удалась: не хватило квоты» требуют разного поведения, поэтому `Комментарий` задания попадает в ответ `pull`.

**Проверено тестами** (`relay/tests/provision-cycle.test.mjs`, 11): задание адресовано спросившему слоту; адрес попадает в лист и закрывает задание; после создания та же карточка выдаётся вместе с адресом; соседний контейнер адрес не наследует; повторный адрес обновляет строку, а не плодит вторую; неудача записывается с причиной и не блокирует пару навсегда; вторая вкладка не получает задание повторно.

**Инварианты.** Созданный агент без адреса не считается готовым — `agent` с пустым `url` отклоняется. Одна пара — одна строка «Экземпляров». Неудача не блокирует пару навсегда.

**Откат.** Убрать действие `agent` из `protocol.mjs` и `agentReady` из службы; вернуть `pull` → «жди» при отсутствии агента. Первое оставит цикл разомкнутым, второе — блокером, которого владелец просил не делать.

## D-013 (1.22.0) — Вход по сервисному аккаунту Google без OAuth

**Дата:** 2026-11-23 · **Статус:** принято.

**Причина.** Запуск с настоящей книгой требовал `RELAY_TOKEN` — токен на час, который надо добывать вручную. Для владельца это означало ежечасное действие, а OAuth-цикл требует браузера, редиректа и согласия — то есть ровно того, чего мы обещали не требовать («упрощённая настройка»). README при этом советовал сервисный аккаунт, которого в коде **не было**: совет не работал.

**Решение.** `relay/src/google-auth.mjs`: разбор ключа (из файла `RELAY_GOOGLE_SA_FILE` или строки `RELAY_GOOGLE_SA_JSON`), подпись JWT алгоритмом RS256 локально через `node:crypto`, обмен подписи на токен в `oauth2.googleapis.com/token`, кеш с обновлением за пять минут до конца. Один обмен на всех: параллельные вызовы ждут один запрос, а не идут в Google каждый. `RELAY_TOKEN` и `RELAY_TOKEN_CMD` остаются как запасной путь.

**Что важно в реализации.** Экранированные переносы в `private_key` восстанавливаются: ключ в однострочной переменной иначе даёт `invalid_grant`, и человек ищет ошибку в книге, а не в переменной. Отказ Google не превращается в пустой токен: причина уходит наверх словами. Срок берётся меньший из обещанного Google и записанного в подписи.

**Инварианты.** Ключ подписывается локально, приватный ключ не уходит по сети. Токен не возвращается как пустая строка при ошибке. Неудачный обмен не залипает: следующая попытка снова идёт в сеть.

**Откат.** Убрать `google-auth.mjs` и ветку `serviceAccount` в `index.mjs`; вернуться к `RELAY_TOKEN`/`RELAY_TOKEN_CMD`. Обе переменные поддерживаются и сейчас.

## D-014 (1.23.0) — Скрипт не пишет в поля, которых нет в базе

**Дата:** 2026-11-23 · **Статус:** принято.

**Причина.** Владелец по совету D-011 удалил из «Ролей» поля `Agent Job ID` и `Agent Created At` — они переехали в лист «Экземпляры». Проверка на живой базе показала: Notion отвечает `validation_error` на **весь** запрос, если в нём есть хоть одно отсутствующее свойство, и не применяет ничего — включая `Agent URL` и `Agent State`. Provisioning вставал бы на каждой роли, а сообщение говорило бы про отсутствующее поле, а не про то, что роль не создана.

Дополнительно нашлись две тихие ошибки того же рода: `12-notion.js` читал удалённые поля без проверки (`rt()` на `undefined` бросает TypeError в шаге цикла), а проверка схемы в мастере считала «Agent State» и «Agent Admin» лишними полями и советовала их удалить — то есть советовала сломать provisioning.

**Решение.**

1. Запись полей `Agent Job ID` / `Agent Created At` / `Previous Agent URL` идёт только после проверки живой схемы (`provisionCanWriteProps`): один `GET pages/{id}`, по нему — какие свойства существуют. Схему не прочитали — необязательные поля не пишутся вовсе, а в журнал идёт `provision_schema_unread`.
2. Чтение в `mapRoleRow` проверяет наличие свойства перед `rt()`.
3. Мастер больше не называет «лишними» поля, которые транспорт читает или пишет: список аддитивных полей «Ролей» перечислен явно, а «Устав» в него намеренно не входит — оно для людей, и человек должен об этом знать.
4. `Agent State` и `Agent Admin` проверяются по типу, если присутствуют, но не требуются: база без них работает по-старому.

**Инварианты.** Ни одно поле не пишется без проверки наличия в живой схеме. Проверка спрашивает живой объект, а не нормализованную строку — иначе она всегда истинна. «Лишнее поле» в мастере значит «не обязательное», а не «ненужное».

**Откат.** Убрать `canWrite` из `provisionPatchNotion` и вернуть безусловную запись. Тогда удаление любого поля в «Ролях» снова будет ломать создание агентов.

## D-015 (1.24.0) — Рабочий адрес роли — пара (роль, слот); «Agent URL» в «Ролях» остаётся только у админских

**Дата:** 2026-11-26 · **Статус:** принято.

**Причина.** Три требования владельца, которые D-011 назвал, но не доделал.

1. «В таблице Роли есть два спорных поля: Agent URL и Previous Agent URL» — и адрес строки действительно перестал быть адресом работы. У роли столько агентов, сколько рабочих контейнеров; сколько бы ни было `Agent URL` в строке, он один. Пока он держал рабочий адрес, всё зависело от того, какой контейнер вписал его последним: три агента одной роли в трёх контейнерах смотрели в одну строку, и задание уезжало не тому.
2. «Обратная связь не должна ждать ходов и не должна стоять за одной неготовой строкой». Прежняя очередь была последовательной: `answerPending()` отдавала `answerQueue()[0]`, то есть одну голову на весь транспорт. Пока её адресат не готов, не двигалась ни одна другая строка.
3. «Отсутствие нужного листа — не повод отказывать». Книга владельца жила без листа «Экземпляры» с 1.20.0: адрес созданного агента было некуда записать, и каждая карточка роли заново требовала создания — снаружи это выглядело как «цикл работает».

**Решение.**

1. **Адрес — пара (роль, слот).** `12b-instances.js` читает «Экземпляры» через службу (`/api/snapshot`, CORS `*`). Порядок доставки: экземпляр пары в своём слоте (слот вкладки определяется по почте аккаунта), затем экземпляр в любом слоте, затем `Agent URL` строки. Строка остаётся запасным путём для админских ролей и старых книг.
2. **`roles()` больше не фильтрует по адресу.** Фильтр `r.id && r.url` остался от времени, когда id выводился из ссылки; после снятия адресов он объявил бы некомплект по каждой неадминской роли. Укомплектованность проверяет `rosterRoleGaps`, и она теперь смотрит на экземпляры.
3. **Очередь приёмки — не очередь, а набор.** `answerPending(exclude)` возвращает первую **свободную** строку (gate-вопросы впереди), `answerInFlight` считает строку занятой по `sendingAt` в пределах `answerSendHoldMs` (120 с). «Свободной нет» больше не значит «очередь пуста»: `continueAfterAnswerReturn` не возвращает план Координатору, пока живы строки.
4. **Книга чинится сама.** `loadInstances` при ошибке чтения создаёт лист из схемы и перечитывает; `readiness` называет недостающие листы, а не отвечает «ok».
5. **«Последняя жизнь» экземпляра обновляется ударом сердца** (`beat`), а не только при создании.

**Инварианты.** Пустой `Agent URL` у неадминской роли — норма, а не недозаполненность. Удаление адреса из строки не отнимает доставку: пара важнее строки. Строка, по которой идёт отправка, занята для всех, но не блокирует остальные. Одна неготовая строка не останавливает ни цикл, ни остальную обратную связь.

**Откат.** Вернуть `r.url` в фильтр `roles()`, `answerQueue()[0]` в `answerPending` и `role.url` в `sendToRole`; тогда неадминские роли без адреса в строке снова не получат карточек, а обратная связь снова станет последовательной.

## D-016 (1.24.1) — Доставка спрашивает адрес у пары, а не у строки «Ролей»

**Дата:** 2026-11-23 · **Статус:** принято.

**Причина.** D-015 убрал `Agent URL` у неадминских ролей и объявил, что рабочий адрес — пара (роль, слот). Но доставка и самоопознание страницы продолжали читать `role.url`: `sendToRole` переходил на `location.assign(role.url)`, `navigateTo` — так же, `tick` искал себя по `roleFromPath()` среди строк «Ролей», а `startAnswer` считал адресата готовым по `named.url`. Пока в книге оставались старые адреса, это было незаметно. Сценарий владельца — удалить всех исполнителей в Arena и посмотреть, как транспорт создаст их сам, — попадал ровно в этот пробел: у первой же созданной рабочей роли адреса в строке нет, значит задание не находит страницу, а страница не опознаёт себя ролью. Плюс `relayBase()` читал `cfn-relay-url`, которого не было ни в одном окне: «Экземпляры» не были видны вообще.

**Решение.**

1. **Одна точка адреса доставки — `roleDeliveryUrl(role)`.** Сначала `role.url` (у админских ролей он там по закону), затем `roleInstanceUrl(role.name)` — пара в своём слоте, затем в любом. Пустой ответ — это причина, названная через `roleAddressWhy`, а не молчаливый переход «в никуда».
2. **Все пути доставки идут через неё:** `sendToRole`, `navigateTo`, сравнение «та же страница» в `tick`, выбор адресата в `startAnswer` (включая запасного Coordinator).
3. **Страница опознаёт себя без адреса в строке:** по `meId` из URL против «Экземпляров», затем по почте аккаунта вкладки (`relayCurrentSlot`). Несколько ролей в одном слоте — не угадываем: журнал говорит, что делать.
4. **Адрес службы Relay виден человеку:** поле «Служба Relay» в окне ⚙, профиль, проверка формы при сохранении (`http://localhost:8787` допустим). Без него пары не читаются, и это сказано в окне, а не только в журнале.

**Инварианты.** Ни один путь доставки не читает `role.url` напрямую. Отсутствие адреса — это сообщение с причиной, а не пустой переход. Пустой `Agent URL` в строке не мешает ни отправке, ни самоопознанию, ни адресату обратной связи.

**Откат.** Вернуть `role.url` в `sendToRole`/`navigateTo`, убрать резолв в `tick` и `startAnswer`, убрать поле «Служба Relay»; тогда после удаления исполнителей транспорт снова не сможет доставить ни одно задание.

## D-017 (1.25.0) — Рабочие запросы к Notion идут через мост, проверка сети остаётся прямой

**Дата:** 2026-11-26 · **Статус:** принято.

**Причина.** После перехода на службу `relay/` (D-009) запросы к `api.notion.com` идут напрямую с машины владельца. VPN-клиент (HAPP/Xray) режет именно этот домен: DNS отвечает, TCP проходит за 8 мс, TLS-рукопожатие не завершается — пульт показывает `UND_ERR_CONNECT_TIMEOUT`, «Найти и применить» и чтение справочника ролей не проходят. Раньше те же запросы шли из браузера через ScriptCat и миновали локальное правило (у Firefox свой сетевой путь), поэтому старая система работала. Мост Apps Script при этом отвечает: живёт он в Google, и локальный фильтр до него не касается.

**Решение.**

1. **`createNotionFetch` в `relay/src/notion-db.mjs`** — fetch для рабочих запросов: сначала мост (действие `notion`), при отказе моста — прямой путь. Моста нет (демо, вход по ключу Google) — обычный прямой fetch, поведение прежних версий.
2. **Действие `notion` в `relay/apps-script/Code.gs`** — запрос к `https://api.notion.com` с путём `/v1/...`: путь проверяется, хост зашит в скрипт, методы ограничены списком, токен приходит на каждый запрос и нигде не хранится. Ответ — `{ok, status, text}`; статус Notion доходит как есть, редирект не скрывается за следованием.
3. **Что НЕ идёт через мост:** проверка сети (`pingNotion`) и диагностика по звеньям (`deepDiagnose`) — им нужен именно прямой путь, иначе пульт сообщил бы «Notion отвечает», пока домен срезан. Через мост идут рабочие пути: поиск баз (`searchDatabases`), справочник ролей (`fetchRoles`), проверка токена поиском.
4. **Старый код в книге — явная ошибка:** если мост отвечает «неизвестное действие», служба просит обновить `Code.gs`, а не прячет это за сетевой ошибкой. Прочие отказы моста (ключ, квота, не JSON) откатываются на прямой путь.

**Инварианты.** Прямой путь остаётся запасным для работы и единственным для диагностики. Ответ Notion (включая 401) не заменяется ответом моста: статус и текст приходят как есть. Ключ моста проверяется до любого действия, `GET` содержимое книги не отдаёт.

**Откат.** Убрать `createNotionFetch` из `server.mjs`/`service.mjs` и действие `notion` из `Code.gs`; при срезанном домене настройка Notion снова не пройдёт, пока локальное правило VPN не снято.

## D-018 (1.25.1) — Версия службы видна в шапке пульта

**Дата:** 2026-11-26 · **Статус:** принято.

**Причина.** После вливания фикса Notion (D-017) владелец обновлял файлы через GitHub Desktop, но не мог проверить, какая сборка бежит: версии не было нигде, кроме страницы `/api/mount`, а номер `1.25.0` стоял и до фикса — его подняли в PR #33 вместе с остальной службой, без отдельного выпуска. Без видимой версии «обновил — и что теперь?» неотличимо от «обновил, но процесс старый»: GitHub Desktop обновляет файлы и не перезапускает службу. Первый симптом путаницы — «проблема на твоей стороне» при обновлённом репозитории и старом окне .bat.

**Решение.**

1. **Шапка пульта показывает версию процесса:** `/api/snapshot` отдаёт `version` из `index.mjs`, `renderHeader` печатает `v…` рядом с названием. Цифра описывает бегущий процесс, а не содержимое репозитория.
2. **Выпуск 1.25.1 — номер, который гарантирует фикс D-017:** любая сборка с `v1.25.1` в шапке содержит `createNotionFetch` и действие `notion`.
3. **Откат на прямой путь виден в консоли:** если мост не ответил и запрос ушёл напрямую, служба печатает причину в окно .bat (`Notion: мост не ответил (…) иду напрямую`) — «мост молчит» и «Notion молчит» больше не выглядят одинаково.

**Инварианты.** Версия приходит со снимком и не кэшируется браузером. Номер поднимает только выпуск вместе с решением; каждый откат на прямой путь назван в консоли.

**Откат.** Убрать `version` из снимка и строку из шапки, убрать печать отката; тогда снова невозможно отличить процесс с фиксом от процесса без него.

## D-019 (1.25.2) — Внешний HTTP моста авторизуется запуском `authorize` в редакторе

**Дата:** 2026-11-26 · **Статус:** принято.

**Причина.** Действие `notion` (D-017) вызывает `UrlFetchApp.fetch`, а на это право — `https://www.googleapis.com/auth/script.external_request` — у скрипта не было выданного согласия: старый мост читал только книгу (`SpreadsheetApp`), и прав на неё хватало с первого развёртывания. Веб-приложение не умеет само показывать окно «Нужны права» — оно отвечает отказом на каждый вызов. Симптом в консоли службы: `Notion: мост не ответил (У вас нет разрешения на вызов функции "UrlFetchApp.fetch"…); иду напрямую`, а владелец видит в пульте ошибку прямого пути, не видя причины.

**Решение.**

1. **Функция `authorize()` в `relay/apps-script/Code.gs`** — запускается в редакторе один раз: вызывает `UrlFetchApp.fetch`, Google показывает окно согласия, владелец жмёт «Допустить». Право выдаётся проекту скрипта, веб-приложение исполняется от его владельца — после этого действие `notion` работает.
2. **Порядок шагов в README и на странице `/api/mount`** содержит шаг авторизации между вставкой кода и развёртыванием; после смены прав публикуется **новая версия** веб-приложения.
3. **Отказ не теряется:** `createNotionFetch` печатает текст отказа моста в консоль и уходит на прямой путь — диагноз читается по строке `Notion: мост не ответил (…)`, а не по догадкам.

**Инварианты.** Ни один шаг установки не требует консоли Google Cloud и ключа Google. Отказ моста всегда назван в консоли службы. Прямой путь остаётся запасным, диагностика — прямой.

**Откат.** Убрать `authorize()` и шаги из README/`mount-page`; тогда новый владелец с новой книгой упрётся в «нет разрешения» без подсказки, что запустить.
